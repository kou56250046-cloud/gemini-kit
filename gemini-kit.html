Gemini 案件キットオフラインで動作・外部送信なし

第 1 部　案件の進め方（案件カルテ）

打合せの記録や資料を Gemini に読ませて「案件カルテ」を作り、分かっていること・聞くべきことを固めます。カルテが案件の事実の正です。文書づくり（第 2 部）のプロンプトにも、カルテの中身が自動で入ります。

第 2 部　文書の作り方（要件定義書・詳細設計書・提示資料）

Gemini には「中身（文章・構造）」だけを書かせ、品質の型と見た目はこのキットが受け持ちます。 資料を一度で完成させず、段階を分け、作る役とレビューする役を分けるのが品質と再現性の要です。

どれを使う？

まず試す：Gem を作らずに始める（5分）

  1. プロンプト集で作りたい文書の「Gem 指示文」（例：要件定義 Gem）を開き、「コピー」を押す
  2. Gemini で新しい会話を開き、最初のメッセージにそのまま貼って送る。続けて「了解したら OK とだけ返して」と送る
  3. プロンプト集の上の「差し込む値」に案件名などを入れ、① ヒアリングをコピーし、案件資料を添付して送る
  4. 以降は各プロンプトの下の「次の段階」ボタンで ② → ③ … と進む
  5. ③ 以降の本文は、Gemini がコードブロック（````markdown）で返します。ブロック右上のコピーで原文を取り、文書ビューに貼って確かめ、「.md で保存」を押す（別の会話で .md に直してもらう必要はありません）

何度も使うようになったら、次の「Gem を作る」に進むと、毎回の貼り付けが不要になります。

1. Gem を作る（何度も使うなら）

Gemini の「Gem マネージャー」で、次の 4 つの Gem を作ります。プロンプト集の「Gem 指示文」をコピーして「カスタム指示」欄に貼り、知識ファイルを追加します（各項目の「.md で保存」で保存したファイル）。 「名前」と「説明」は一覧で見分けるためのもので、ルールは書きません（説明は空欄でもかまいません）。各 Gem 指示文の「使いどころ」に記入例があります。

Gem指示欄に貼るもの知識ファイルに入れるもの
要件定義要件定義 Gem要件定義書チェックリスト／模範例：要件定義書／フロー記法
詳細設計詳細設計 Gem詳細設計書チェックリスト／模範例：詳細設計書／フロー記法
顧客提示資料顧客提示資料 Gem顧客提示資料チェックリスト／スライド JSON／フロー記法／模範例：顧客提示資料／デザイン原則／図表の選び方（デザイン（PPT）の残りも入れるとさらに安定）
レビューレビュー Gem3 種類のチェックリストすべて

案件の資料（議事録・承認済みの要件定義書など）は知識ファイルに入れず、会話ごとに添付してください。 知識ファイルに入れると、次の案件でも残り、別の顧客向けの資料に混ざります。
模範例はダミーです。実案件の良い成果物で差し替えるときは、マスキングと「マスキング後の残存チェック」を通してから入れてください。

2. 文書を作るたびに：段階を分けて進める

流れは先頭の「全体の流れ」の図のとおりです。補足：

  • プロンプト中の {{案件名}} などは、プロンプト集の上の「差し込む値」に入れておくと、コピー時に置き換わります。案件ごとに「この値を案件として保存」しておけば、次回は呼び出すだけです。
  • 3 章（設計なら 5 単位）書くごと、または回答が雑になってきたら「会話の引き継ぎ」を送り、出力を新しい会話の最初に貼ります。
  • ①で出る事実一覧（F-01…）はメモ帳などに保存しておき、④レビューのときに一緒に貼ります。本文に反映されていない事実が見つかります。
  • ④レビューの結論が「差し戻し」（致命項目が NG）なら必ず直します。⑤修正は2回まで。それでも直らなければ人が直します。
  • 人が直した点（削った・足した）はメモしておき、同じ指摘が続いたらチェックリストや Gem 指示文に書き足します。

案は1つか、複数か

対象やり方
現状（As-Is）の業務フロー1案。事実を写すので案は分けない。まず分岐なしで全体を描き、次に例外を足す
新しい業務・方式・構成（To-Be）②で2〜3案と「何もしない」を比べ、人が1つに決める。重み付きの比較表と、点数以外の理由を見て選ぶ（②' 案の比較）
詳細設計・本文推奨1案で書く。判断が分かれる論点だけ「対案・その案が勝つ条件・失うもの」を1行で併記する
顧客提示資料提案する方式は比べて決め、資料では推奨と比較（compare / table）を見せる

レビュー Gem の確かめ方（最初に一度）

レビュー Gem が欠陥を見逃さないかを、わざと欠陥を入れた文書で確かめます。 プロンプト集の確認用：欠陥入りの要件定義書の「事実一覧」と「レビューする文書」を「④ レビュー」に貼って送り、末尾の正解表の12件を見つけられるかを比べます。 見落とした欠陥があれば、チェックリストのその項目に合格例・不合格例を足すなどして直します。Gem 指示文やチェックリストを変えたときも、もう一度確かめます。

決まった流れ以外の場面では、プロンプト集の「応用プロンプト」を使います。

場面使うプロンプト
打合せの記録から始める議事録・打合せメモの整理 → 出力を「② 骨子」の回答欄に貼る
承認済みの文書に変更が入った既存文書の改訂（影響範囲 → 改訂 → 改訂履歴。ID は振り直さない）
受入テストを準備する受入テスト仕様書 → 出力をトレーサビリティタブに貼ると、テストのない要件が分かる
見積もりの根拠をそろえる見積もりの前提と WBS（金額は出させず、作業の分解・前提・リスクだけ）

5. 保存について

  • プロンプトの編集・差し込む値・フロー図とスライドの入力・配色は、このブラウザに自動保存されます。別の PC やブラウザには引き継がれません。
  • ブラウザのデータを消すと編集内容も消えます。設定の「書き出し」で、定期的に JSON に保存してください。
  • トレーサビリティ・マスキング・判断・データに貼った内容は保存しません（画面を閉じると消えます）。判断・データは「まとめて保存」で .md に残せます。
  • このファイルはネットワークに一切接続しません（外部への送信・読み込みを禁止する設定を入れています）。

フロー図

Gemini が書いたフロー記法を貼ると、自動で配置して描きます。箱と帯はレーン（役割）ごとに色が分かれます。レーンかノードに {AI} {ルール} {人} {外部} を付けると、処理の区分ごとに決まった色（AI は紫・ルールは青・人は橙・外部は灰）で塗り、箱の左上に区分名（分岐なら「AI判断」「ルール判定」）と、図の下に凡例を出します。どの図でも同じ区分は同じ色です。分岐の線は、ラベルが「はい・OK・承認」なら緑、「いいえ・NG・差し戻し」なら赤、それ以外は出口ごとに別の色になります。

    スライド

    Gemini が書いたスライド JSON を貼ると、16:9 でプレビューします。

      文書ビュー

      Gemini が出した Markdown（要件定義書・詳細設計書など）を貼ると、目次・ID のリンク・【仮置き】【要確認】の一覧（表の「状態」列の分も数えます）・状態での絞り込み・フロー図つきの読みやすい文書にします。案件を選んでいれば、F-xx などにマウスを重ねるとカルテの引用が出ます。Gemini のコードブロック（````markdown）ごと貼っても、囲みを外して読みます。「.md で保存」で原文を .md にできます。貼った内容は保存しません。

      更新の影響（開いた全ファイル）

      カルテの最新版と照らして、直すファイルを出します。比べる元の版は、設計書を書いた時点の版を選んでください。

      トレーサビリティ

      要件定義書と設計書の本文を貼ると、要件 ID（例：REQ-001）が設計のどこで参照されているかを表にします。設計の区切りは「## FNC-001 〜」のように設計 ID で始まる行、または見出しです。貼った内容は保存しません。

      マスキング

      Excel で範囲をコピーして貼り付けます（CSV も可）。処理はこのブラウザの中だけで行い、貼った内容は保存しません。同じ値には同じ仮名を付けます（「対応表を空にする」まで、続けて貼った別の表でも同じ仮名になります）。

      設定

      スライドとフロー図の配色

      バックアップ

      プロンプトの編集・差し込む値・フロー図とスライドの入力・配色を JSON に保存します。別の PC へ移すときも使います。

      読み込むと、いまのプロンプトの編集・差し込む値・フロー図とスライドの入力・配色がすべて置き換わります。必要なら先に「書き出し」で保存してください。

      初期化

      このブラウザに保存した内容をすべて消し、配布時の状態に戻します。消す前に、バックアップの JSON を自動で保存します。
